wrong row (107683 or 107687)". RESEARCH found both rows carry IGDBId 267639 with a 2018-12-25
release date, which matches neither the 1998 nor the 2004 original. The script therefore corrects
*every* row whose looked-up ID differs; if that turns out to be both rows, the checkpoint says so
explicitly. This follows D-08's intent ("fix any found the same way"), not a scope change.

**Flagged assumption A1/A2 (RESEARCH).** The IGDB `external_games` lookup and the unofficial
"Half-Life 2 = 233" lead are not used as authority. The authority is the app's own IGDB search
plus the user's confirmation at the checkpoint.

**Flagged assumption — GameTags provenance.** `GameSyncManager` fills `GameTags` from IGDB themes
only when empty. If another code path (Steam import or `GameEnrichmentManager`) also writes
`GameTags`, clearing them would destroy non-IGDB data, so Task 1 checks provenance before deciding.

**Convention exemption — raw guarded writes, no stored procedure (user approval required).**
CLAUDE.md says stored procedures only for insert/update/delete. Script 38 is a one-off, numbered
data-correction script, not an application write path, so it runs raw `IF EXISTS`-guarded
`UPDATE`/`DELETE` statements and adds no SP: a stored procedure used exactly once and then left in
the schema is an unnecessary abstraction (CLAUDE.md). No existing SP performs this change —
`sp_UpsertIGDBGame` (script 34) is keyed on `(IGDBId, UserId)` and cannot change `IGDBId`, and
`sp_UpdateGameCover` (script 11) stamps `LastImageSyncDate = GETUTCDATE()` instead of clearing it.
Numbered scripts already write one-off data without an SP (the guarded `INSERT INTO WorkerStatus`
seeds in scripts 30 and 37). This is a deliberate exemption, not an oversight: the user approves it
at the decision checkpoint as part of `apply-user`, and the script header records it.

**Canon-referral breadcrumb:** SQL injection is canon (`/gsd-secure-phase`); script 38 uses only
literals, no dynamic SQL.
