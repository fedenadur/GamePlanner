<objective>
Close the folded IGDBId cross-user collision bug: make `Games.IGDBId` non-unique so two users
can each own their copy of the same IGDB title, reduce the orphaned `sp_UpsertIGDBGame` to a
strictly scoped update that can never create a row, and make the games list say something when
a delete fails.

Purpose: this is a data-integrity bug that has already been observed destroying user data —
manually added games flipping to `IsActive = 0` on their own within minutes. A fix was drafted
in the working tree but never applied, and the drafted procedure carries a second defect of its
own (an insert path that would create games with empty genres and a hardcoded estimate). Both
halves land here.

Scope note: the folded todo has no requirement ID of its own. It is carried under REL-01
because it is a data-layer write-path reliability defect in the same `GameManager` surface, and
because Phase 2's context flagged it as a natural fit for this phase. REL-01's own acceptance is
satisfied by plan 04-01, not here.

Output: an applied and corrected pair of migration scripts, a verified-safe set of remaining
`IGDBId` consumers, and a delete action that tells the user when it fails.
</objective>

## Assumptions & unresolved rows

**Flagged assumption — the todo's root-cause attribution is not confirmed by static analysis.**
The folded todo attributes the observed auto-deactivation to `sp_UpsertIGDBGame` combined with
the unique index. Planning checked both halves of that claim against the current tree and found:

- A repo-wide search for a write of `IsActive = 0` across every `.cs` and `.sql` file returns
  **exactly one** site: `sp_DeleteGame` in `Database/03_StoredProcedures.sql` line 59.
- A repo-wide search for `sp_UpsertIGDBGame` across `GamePlanner.API` returns **no C# caller**
  at all — the procedure is orphaned, exactly as `04-CONTEXT.md` D-04 states.

So applying script 34 alone cannot be the operative fix; the load-bearing change is script 33
(removing the unique index) plus the `(IGDBId, UserId, IsActive)` dedup check already present in
`GameManager.CreateFromIgdbAsync`. This row stays **unresolved** at plan time and is closed
empirically by Task 3's live re-verification, which must capture the actual mechanism before the
todo is marked done. It is recorded here rather than silently assumed away.

**Residual risk (accepted, recorded).** Removing the global unique index also removes the
database-level guarantee that a *single* user cannot end up with two active rows sharing one
`IGDBId`. Two sites key a dictionary on `IGDBId` and would throw on such a duplicate:
`CalendarController.cs` line 65 and `TrackedGamesManager.cs` line 30. Both filter by
`g.UserId == userId && g.IsActive` first, so the cross-user case is safe; the within-user case is
prevented at the application layer by the `CreateFromIgdbAsync` dedup check. Task 2 asserts both
filters are intact.

**Canon-referral breadcrumb (surfaced, deliberately not minted as a prohibition):** SQL injection
in the rewritten procedure is canon — the procedure is fully parameterised and coverage belongs to
`/gsd-secure-phase`, not to a bespoke prohibition here.
