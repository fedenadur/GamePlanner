<objective>
Extend the existing `WorkerStatus` record so a sync run can report "completed, but N items failed" without lying about the run's overall outcome, and without inventing a new table, endpoint, or UI.

Purpose: REL-03's ROADMAP wording is "surfaced rather than silently dropped". D-16 chose the existing `WorkerStatus` table and the existing `GET /api/worker/status` endpoint as the surfacing mechanism. This plan lands that contract so plan 02-03 has somewhere to report to.
Output: two nullable columns, a backward-compatible manager signature, and the numbered migration script that adds them.
</objective>

Add nothing else — no attributes, no constants, no `WorkerStatusValue` changes. `int?` rather than `int` is deliberate: null means "this worker does not track item-level failures", which is honest for the workers that plan 02-03 leaves uninstrumented; a non-nullable zero would assert a count that was never taken.

3. `Database/35_AlterWorkerStatus_AddFailureTracking.sql` — new file, numbered 35 (confirm at execution time that no `35_` file has appeared; `34_FixStoredProcedure_UpsertIGDBGame.sql` is the current highest and is untracked in the working tree). ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application → `WorkerStatus` table | Free-text failure detail crosses from exception-handling code into persistent storage |
| `WorkerStatus` table → `GET /api/worker/status` | The row is serialised verbatim to any authenticated caller — every column is an outbound disclosure surface |
| Developer → SQL Server (SSMS) | A hand-run DDL script alters a live table |
