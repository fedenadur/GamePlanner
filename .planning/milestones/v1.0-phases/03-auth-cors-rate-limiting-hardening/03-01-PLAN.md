<objective>
Reconfigure the `GamePlanner.API` composition root so the JWT contract, the CORS
contract, and the request-rate contract all match the app's real trust boundary —
proven end-to-end on a single request path before any of it is broadcast across the
rest of the API surface.

Purpose: `Program.cs` is the one file every decision in this phase passes through, and
it carries the phase's single architectural risk. The current pipeline runs
`UseRateLimiter()` *before* `UseAuthentication()`, so a partition function that reads
`HttpContext.User` would see an unauthenticated principal and silently drop every
caller into one shared bucket (RESEARCH.md Pitfall 2). Proving the reordered pipeline
against a real 429 on a real endpoint is what makes the rest of the phase mechanical.

Output: A hardened `Program.cs`, a 24-hour JWT lifetime in `AuthService.cs`, and one
mutation endpoint bound to the new per-user `"mutations"` policy with an end-to-end
proof that partitioning actually partitions.
</objective>

<assumption_delta_decision>
The `assumption-delta` detector fired on `pluralization` (term `another`, from ROADMAP
success criterion 5: *"one user's rejections don't affect another user's requests"*).

- **Primary noun:** the authenticated user, identified by the JWT `ClaimTypes.NameIdentifier`
  claim. Rate limiting is being promoted from *no identity at all* to *the same identity
  noun the rest of the app already scopes every query by*.
- **Decision: `add-alongside`.** The pre-existing `"auth"` policy stays a single
  unpartitioned global bucket while the new `"mutations"` policy is per-user. This is a
  deliberate asymmetry, not carried-over debt: `"auth"` guards `POST /api/auth/login`
  and `/register`, which run *before* any JWT exists, so there is no authenticated
  identity available to partition on at that boundary.
- **Accepted debt / what would force a promote:** if brute-force traffic from a single
  source ever starts rate-limiting legitimate logins app-wide, `"auth"` must be promoted
  to a partitioned policy keyed on `Connection.RemoteIpAddress`. That is out of scope
  here (D-09 fixes this phase's scope to Games/Journal/Session mutations).
- **Companion invariant (adopted):** Plan 03-02 asserts that *every* POST/PUT/DELETE
  action across the three in-scope controllers carries the policy attribute, so a future
  phase adding a mutation endpoint without it goes red rather than landing silently.
</assumption_delta_decision>

**1. `Program.cs` — register the `"mutations"` policy.** Inside the existing
`builder.Services.AddRateLimiter(options => { ... })` call, leave the `"auth"` registration
exactly as it is and add a second policy named `mutations` registered through
`options.AddPolicy<string>("mutations", httpContext => ...)`. The partitioner reads
`httpContext.User.FindFirstValue(ClaimTypes.NameIdentifier)`, falls back to the string
`anonymous` when the claim is absent, and returns
`RateLimitPartition.GetFixedWindowLimiter(<that key>, _ => new FixedWindowRateLimiterOptions { PermitLimit = 100, Window = TimeSpan.FromHours(1), QueueProcessingOrder = QueueProcessingOrder.OldestFirst, QueueLimit = 0 })`
per D-10/D-11. Use `AddPolicy<string>` and **not** the unpartitioned convenience overload
that the `"auth"` policy uses — that overload takes no partition-key function and would
give every caller one shared bucket (RESEARCH.md Pitfall 1). Add
`using System.Security.Claims;` to the file's import block; `System.Threading.RateLimiting`
is already imported at line 2.

**2. `Program.cs` — register the `OnRejected` callback (D-15, OBS-01).** In the same
`AddRateLimiter` options block, set `options.OnRejected` to a callback that emits one
structured `LogWarning` before returning `ValueTask.CompletedTask`. It must carry three
named parameters: the user id from `ClaimTypes.NameIdentifier` falling back to
`context.HttpContext.Connection.RemoteIpAddress?.ToString()` and then to the string
`unknown`; the request path from `context.HttpContext.Request.Path`; and the policy name
read from
`context.HttpContext.GetEndpoint()?.Metadata.GetMetadata<EnableRateLimitingAttribute>()?.PolicyName`.
The message template must contain the literal text `Rate limit rejected` so it is
greppable. Obtain the logger inside the callback from
`context.HttpContext.RequestServices.GetRequiredService<ILoggerFactory>()` (the options
lambda runs at registration time, before the service provider exists). Use named
placeholders in the message template, never string interpolation — match the
`logger.LogError("IGDB error {Status}: {Body}", ...)` convention in `IgdbService.cs`.

**3. `Program.cs` — reorder the pipeline (RESEARCH.md Pitfall 2, non-optional).** The
registration block at the bottom of the file currently runs the rate limiter before
authentication. Move `app.UseAuthentication();` so it runs immediately after
`app.UseCors("AllowAngular");` and immediately before `app.UseRateLimiter();`, leaving
`app.UseAuthorization();` and `app.MapControllers();` after both. Final order:
`UseHttpsRedirection` → `UseCors` → `UseAuthentication` → `UseRateLimiter` →
`UseAuthorization` → `MapControllers`. Without this, `HttpContext.User` is an anonymous
principal when the partitioner runs and every caller collapses into the `anonymous`
partition.

**4. `AuthService.cs` — 24-hour token lifetime (D-01, AUTH-01).** The `expires:` argument
of the `JwtSecurityToken` constructor in `GenerateToken` (line 71) currently produces a
seven-day expiry. Replace that expression with `DateTime.UtcNow.AddHours(24)`. Change
nothing else in `GenerateToken` — the claim set, issuer, audience and signing credentials
stay exactly as they are (D-02: no frontend or UX change accompanies this).

**5. `GamesController.cs` — bind the tracer endpoint.** Add
`using Microsoft.AspNetCore.RateLimiting;` to the import block and put
`[EnableRateLimiting("mutations")]` on the `Delete` action (line 86-93) only. `Delete`
is the tracer endpoint because a DELETE against a non-existent id returns 404 without
writing any data, so the 101-request proof below leaves the database untouched. The
