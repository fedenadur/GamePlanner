<objective>
Advance `game-planner-ui` from Angular 14 to Angular 17 through three sequential single-major hops
(14 -> 15, 15 -> 16, 16 -> 17), each fully verified and separately committed.

Purpose: Angular's CLI migrates one major at a time by design; skipping a major means that major's
mandatory codemods never run, which is the single most common cause of silent breakage in this kind
of upgrade. Hop 4 (v17) is also where the CLI first offers the esbuild `application` builder — the
first real opportunity to accidentally leave the "pure dependency bump" scope of D-03.
Output: The app running on Angular 17, with three bisectable hop commits.

**Target for the phase is Angular 22** — see `01-01-PLAN.md` &gt; `<target_version_resolution>` for why
v22 rather than v21, and how to override if v21 was intended.
</objective>

<hop_protocol>
## The hop loop — identical for all three tasks in this plan

Every task below is the same loop with a different version number. It is stated once here and
referenced by each task rather than repeated three times.

1. **Update.** From `game-planner-ui/`, run `ng update` for `@angular/core` and `@angular/cli` both
   pinned to the same target major, via `npx ng` so the project-local CLI runs (a global/local CLI
   mismatch is a known source of confusing mid-chain failures). Never pin TypeScript, zone.js or
   RxJS by hand — `ng update` picks patch versions inside the peer ranges, and the task's acceptance
   criteria assert the result landed in range.

2. **Decline every optional migration (D-03, D-06).** Specifically: conversion of components to the
   standalone (NgModule-free) authoring format; conversion of templates to the built-in control-flow
   block syntax; the `use-application-builder` esbuild/Vite build-target switch (first offered at
   v17); the Vitest test-runner switch; and any prompt offering to drop zone.js in favour of
   Angular's zoneless change-detection provider. Accept only migrations `ng update` applies
   automatically as mandatory codemods. Running non-interactively already produces this behaviour —
   mandatory migrations run, named optional schematics do not, and no extra flag is needed.

3. **Peer-resolution fallback only if needed.** If `ng update` aborts with an `ERESOLVE` /
   peer-dependency conflict *before* running any schematic, retry the same command once with
   `--force`. That flag skips the peer compatibility check, not the install, and still runs the
   schematics. Never use it pre-emptively and never use it to silence a compile error. Record in the
   SUMMARY which hops needed it.

4. **Node runtime band.** Use the Node.js column of RESEARCH.md's hop matrix as the authority for
   each hop, and the Node strategy recorded in `01-01-SUMMARY.md`. If the Angular CLI refuses to run
   with an unsupported-Node-version error, switch to the Node version that hop declares (per D-02,
   changing the local Node runtime is in scope — do not stop to ask) and re-run.

5. **Verify in this order (D-04).** `npm run build`; then
   `npm test -- --watch=false --browsers=ChromeHeadless`; then the karma-builder assertion; then a
   boot smoke check (start the dev server on port 4200, poll until it answers, confirm the served
   HTML contains the app-root element, stop the server). **A test run reporting "Executed 0 of 0"
   with exit 0 is a PASS** — this repo has zero `.spec.ts` files by design (`angular.json` sets
   `schematics.skipTests: true`), so the check proves the Karma/Jasmine harness boots and the builder
   resolves. Only a non-zero exit or a harness/compilation error is a failure.

6. **Structural-preservation check before committing (D-03, D-06).** `src/main.ts` still bootstraps
   the root NgModule via `platformBrowserDynamic()`; `src/app/app.module.ts` still carries a
   `declarations:` array; `src/polyfills.ts` still imports zone.js; `tsconfig.json` still has
   `"strict": true` plus all four `angularCompilerOptions` strictness flags `true`. If a mandatory
   migration proposes loosening a strictness flag, do not accept it silently — stop and report,
   because that trades away a type-safety guarantee this project deliberately opted into.

7. **Commit exactly one commit per hop (D-05)**, message `chore(deps): upgrade Angular N-1 -> N`,
   staging only paths under `game-planner-ui/`. Do not batch two hops into one commit — one commit
   per major is what preserves bisectability.

Work exclusively inside `game-planner-ui/`. `GamePlanner.API/` and `Database/` must remain untouched
— Phase 1 is deliberately isolated from the backend so any regression is attributable to the
frontend alone.
</hop_protocol>
