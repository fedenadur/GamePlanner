<objective>
Broadcast the per-user mutation rate limit proven in plan 03-01 across every in-scope
mutation endpoint, and close the cross-user data leak in the session planner that was
folded into this phase.

Purpose: plan 03-01 proved the `"mutations"` mechanism works on one endpoint. NET-03's
requirement is that it covers the game, journal and session write paths — an endpoint
without the attribute is silently unprotected. The folded todo rides along here because
its fix location, `SessionController`, is the same file that needs the attribute and is
the one in-scope controller with no user-id extraction at all.

Output: All ten in-scope mutation actions bound to the `"mutations"` policy, and both
session-planner queries scoped to the calling user.
</objective>

## Planner finding — the folded todo's fix location is wider than the source artifacts record

CONTEXT.md, RESEARCH.md and PATTERNS.md all name `SessionManager.cs:15` as the single fix
location for the folded cross-user leak. The todo's own reproduction, however, was against
`POST /api/session/plan`, which routes to `SessionController.Plan` →
`SessionPlannerManager.GetRecommendationsAsync` — **not** `SessionManager`. Reading
`SessionPlannerManager.cs` during planning confirms line 38-39 builds `db.Games.Where(g => g.IsActive)`
with no `UserId` predicate, exactly like `SessionManager.cs:15`.

Both managers leak. Fixing only the documented one would leave the *actually reproduced*
endpoint unfixed, so this plan fixes both. The mechanism is identical (thread `userId`
through, add the predicate) and the incremental cost is one parameter and one clause.

Close the cross-user data leak on both session endpoints and bring both under the
mutation rate limit.

**1. `SessionController.cs` — add the user-id helper.** Add
`using System.Security.Claims;` and `using Microsoft.AspNetCore.RateLimiting;` to the
import block. Add a `private int? GetUserId()` method identical to the one in
`GamesController` (lines 95-99): read `User.FindFirstValue(ClaimTypes.NameIdentifier)`
and return `int.TryParse(claim, out var id) ? id : null`. Copy the existing helper rather
than inventing a variant — `GamesController` and `GameJournalController` already carry byte-identical copies.

**2. `SessionController.Recommend`** — after the existing
`AvailableMinutes`/`Mood` validation, call `GetUserId()`, return `Unauthorized()` when it
is null, and pass `userId.Value` as the second argument to
`manager.GetRecommendationAsync(request, userId.Value)`. Add
`[EnableRateLimiting("mutations")]` beneath the `[HttpPost("recommend")]` attribute.

**3. `SessionController.Plan`** — call `GetUserId()`, return `Unauthorized()` when it is
null, and pass `userId.Value` into
`planner.GetRecommendationsAsync(request, userId.Value, ct)`. Add
`[EnableRateLimiting("mutations")]` beneath the `[HttpPost("plan")]` attribute. Both
Session actions are POST, so both are in scope under D-09.

**4. `SessionManager.GetRecommendationAsync`** — change the signature to
`(SessionRequest request, int userId)` and add `g.UserId == userId` to the existing
`.Where(...)` predicate on `db.Games`, so it reads
`g.IsActive && g.UserId == userId && g.EstimatedMinutes <= request.AvailableMinutes`.
This stays an EF LINQ read, matching the project rule that stored procedures are only for
insert/update/delete. Change nothing about the mood-matching or fallback branches below it.

**5. `SessionPlannerManager.GetRecommendationsAsync`** — change the signature to
`(SessionPlannerRequest request, int userId, CancellationToken ct)` and add
`g.UserId == userId` to the `.Where(g => g.IsActive)` predicate on `db.Games` at line 38-39,
so it reads `.Where(g => g.IsActive && g.UserId == userId)`. This is the query the folded
todo actually reproduced against (`POST /api/session/plan`); the source artifacts named
only `SessionManager`, but leaving this one unfiltered would leave the reported leak open.
Leave the `db.GamesHLTB` lookup alone — `GameHLTB` is shared reference data with no
`UserId` column, not per-user library data.
