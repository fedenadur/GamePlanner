Output: a tracked hook source, an install script, the hook installed locally, and a documented one-time setup step.
</objective>

**Install the binary.** Run `winget install --id Gitleaks.Gitleaks --exact` — gitleaks, not trufflehog, per D-10 (single static binary, native Windows support, no Python/Go toolchain, fast default ruleset that catches API-key/JWT-secret patterns). Before accepting the install, confirm from the winget output that the resolved package publisher/source is the official `Gitleaks.Gitleaks` entry pointing at the `gitleaks/gitleaks` GitHub project — this is the provenance check that stands in for a registry legitimacy audit, since gitleaks is a standalone Go binary with no npm/NuGet/PyPI entry to verify. Do not download a loose executable from a mirror. Record the installed version in the SUMMARY. Open a fresh shell afterwards so the updated PATH is visible, and confirm with `gitleaks version`.

**Author `scripts/pre-commit`** as a POSIX `sh` script with a `#!/bin/sh` shebang — Git for Windows runs hooks through its bundled Git Bash `sh`, so no WSL or Cygwin dependency is introduced. Structure:
  - First, a PATH-existence guard using `command -v gitleaks`. If the binary is absent, print a single-line warning that names the install command and then `exit 0`. This branch is not hypothetical: RESEARCH confirms gitleaks is not currently installed on this machine, so it is the state the hook starts from, and D-13 makes letting the commit through the required behaviour rather than a fallback.
  - Then pipe the staged diff into gitleaks with `git diff --cached | gitleaks stdin`. Use this stdin-piping invocation, not the pre-8.19.0 staged-scan subcommand — that older form still functions but has been hidden from `--help` since gitleaks 8.19.0, and current documentation demonstrates the stdin form (RESEARCH Pitfall 1).
  - On a zero exit from gitleaks, `exit 0`. On a non-zero exit, print two lines — that a potential secret was detected in the staged changes and that the commit is blocked, and that the developer should review the findings above, remove the secret and re-stage — then `exit 1`.
  - Keep the script ASCII-only so it renders identically in every terminal the developer uses.

**Author `scripts/install-git-hooks.ps1`** as a PowerShell script, matching the repo's primary shell. It should resolve the repository root from its own location, copy `scripts/pre-commit` to `.git/hooks/pre-commit`, overwrite an existing file, and print a confirmation naming the destination path. Because a Windows filesystem has no executable bit that git honours, also invoke `git update-index --chmod=+x` on the tracked source so a Linux or macOS clone gets an executable hook; wrap that in a check so the script does not fail when the bit is already set. Fail loudly with a non-zero exit if `.git/hooks` does not exist rather than silently doing nothing.

**Run the installer** so `.git/hooks/pre-commit` exists locally. Note in the SUMMARY that this file is deliberately untracked — git never tracks its own hooks directory, which is precisely why D-12 required the install script instead of `core.hooksPath`.

**Document the setup in `CLAUDE.md`** using a scoped `Edit`, never a whole-file `Write`. Add a short "Local setup (one-time)" section after the existing "Commands" section containing:
  - the command to install gitleaks and the command to run `scripts/install-git-hooks.ps1`, with a one-line note that the hook warns and allows the commit when gitleaks is missing;
  - that the four secrets `IGDB:ClientId`, `IGDB:ClientSecret`, `Steam:ApiKey` and `Jwt:Secret` are not in `appsettings.Development.json` and must be set with `dotnet user-secrets set` from `GamePlanner.API/`, using `GamePlanner.API/appsettings.Development.json.example` as the key reference (D-03, D-09);
  - that outside Development the same four keys come from the environment variables `IGDB__ClientId`, `IGDB__ClientSecret`, `Steam__ApiKey` and `Jwt__Secret`, using the ASP.NET Core double-underscore convention (D-04).
Keep the section as terse as the rest of the file — the project's own behaviour rules ask for concision.

<flagged_assumptions>
Spec-less probe fallback — one edge-probe row for this requirement could not be resolved and is recorded here rather than dropped:

**CRED-05 / `unclassified`** — probe: *"unclassified — review manually"*. The probe's shape taxonomy (empty / encoding / concurrency / ordering) targets data-shaped behaviour inside the application; a git hook is dev tooling that lives entirely outside the app's runtime tiers, so no category applies. Per the fallback protocol an `unclassified` row stays unresolved and is surfaced, never auto-backstopped.

- **Assumption made:** the only two behaviours that matter for this requirement are the hook's two branches — binary present, secret staged, commit blocked; and binary absent, warning printed, commit allowed — and both are encoded as executed acceptance criteria in Task 2 rather than as a probe-derived edge predicate.
- **Risk if wrong:** a third branch exists that neither check covers, most plausibly a gitleaks exit code that means neither "clean" nor "finding" (a malformed invocation, or a future version changing its exit-code contract). The hook treats every non-zero exit as a block, which fails closed on the commit but could block the developer on a tooling error — the opposite of D-13's intent. If that is ever observed in practice, the guard needs to distinguish a findings exit from an error exit, and this assumption should be reopened.
</flagged_assumptions>
