<objective>
Make the two remaining classes of security-relevant rejection visible in the application's
log stream: failed login attempts, and requests arriving from an origin the CORS policy
does not allow.

Purpose: OBS-01 requires failed logins, CORS rejections and rate-limit rejections to all
land in a central log stream. Plan 03-01 covered rate-limit rejections. The auth path has
**no logger injected at all** today, so a brute-force attempt against this API currently
leaves no trace. CORS is harder: ASP.NET Core's CORS middleware has no `OnRejected`
equivalent — a disallowed origin simply gets no `Access-Control-Allow-Origin` header and
the *browser* does the blocking, so the server never sees an error to log. D-16 resolves
this with an observation-only middleware placed ahead of `UseCors`.

Output: `ILogger<AuthService>` wired with a warning on both login failure branches, and a
new `CorsRejectionLoggingMiddleware` registered ahead of the CORS middleware.
</objective>

the DI registration via last-registration-wins semantics — is **not exercised by this

DI-ordering risk that has not been grounded, and D-16 plus the project's
"no unnecessary abstractions" rule both point at the simpler middleware.

  <action>
Create the project's first custom middleware and place it where an origin mismatch is
observable.

**1. Create `GamePlanner.API/Middleware/CorsRejectionLoggingMiddleware.cs`.** The
`Middleware/` directory does not exist yet — create it. Use the file-scoped namespace
`GamePlanner.API.Middleware`, matching the convention in `Managers`/`Services`. Declare
`public class CorsRejectionLoggingMiddleware(RequestDelegate next, ILogger<CorsRejectionLoggingMiddleware> logger, IConfiguration config)`
with a single `public async Task InvokeAsync(HttpContext context)` method. Inside:

- Read `context.Request.Headers.Origin.ToString()` into a local, and
  `config["App:FrontendUrl"]` into another — the same key the CORS policy reads, so the
  two can never disagree.
- Log **only** when the origin string is non-empty **and** does not equal the configured
  value under `StringComparison.OrdinalIgnoreCase`. The non-empty guard is mandatory:
  same-origin requests, Swagger UI, curl and server-to-server calls send no Origin header
  at all, and treating those as rejections would flood the log with noise instead of
  signal (RESEARCH.md Pitfall 3).
- The log call is a single `logger.LogWarning` using the template
  `"CORS rejection: Origin {Origin} does not match configured {AllowedOrigin} for {Method} {Path}"`
  with `origin`, the configured value, `context.Request.Method` and `context.Request.Path`
  as the four arguments. Named placeholders only, no string interpolation.
- Always `await next(context)` at the end, on every path. This middleware observes and
  never decides: it must not short-circuit, must not write a response, must not set a
  status code, and must not touch any `Access-Control-*` header. `UseCors` remains solely
  responsible for the actual CORS outcome.

**2. Register it in `Program.cs`.** Add
`app.UseMiddleware<GamePlanner.API.Middleware.CorsRejectionLoggingMiddleware>();` between
`app.UseHttpsRedirection();` and `app.UseCors("AllowAngular");`. Placement is load-bearing:
`UseCors` short-circuits a preflight OPTIONS with a 204, so anything registered after it
never sees a rejected preflight. Do not disturb the
`UseCors` → `UseAuthentication` → `UseRateLimiter` → `UseAuthorization` ordering that plan
03-01 established — the mutation limiter's per-user partitioning depends on it.

Do not implement the `ICorsService` decorator variant documented as a fallback in
RESEARCH.md; this app has one CORS policy and one origin, which is exactly the case the
primary pattern covers.
  </action>
