<objective>
Advance `game-planner-ui` from Angular 20 to Angular 21 (the eighth of nine hops), then upgrade the
local Node.js runtime so the machine satisfies Angular 22's engine range — the two prerequisites for
the final hop in plan `01-05`.

Purpose: v21 is where the CLI switched its new-project test-runner default to Vitest, the single
change most widely misreported as "Karma removed". Separately, the installed Node `v24.14.0` is one
patch short of Angular 22's `^24.15.0` requirement — a gap that is invisible until the final hop
fails. Closing both here means plan `01-05` faces only one variable: the TypeScript 6.0 major jump.
Output: The app running on Angular 21 on a Node runtime that can run Angular 22.

**Target for the phase is Angular 22** — see `01-01-PLAN.md` &gt; `<target_version_resolution>`.
</objective>

Angular 22 declares its engine range as `^22.22.3 || ^24.15.0 || ^26.0.0`. The machine's installed
`v24.14.0` does NOT satisfy `^24.15.0` — that range means `>=24.15.0 <25.0.0`, and 24.14.0 is one
minor short. This is easy to miss because it looks close enough, and npm's own engines check is only
a warning; the Angular CLI performs its own stricter assertion and will refuse to run. Fix it now,
before the final hop, so plan `01-05` faces only the TypeScript 6.0 variable (D-02).

Choose the path of least disruption: bump within the installed Node 24 line to the latest 24.x, which
stays inside `^24.15.0`. Do not jump to Node 26 — that is a larger change with no benefit here, and
Node 22.22.3 would be a downgrade.

If `01-01-SUMMARY.md` records that nvm-windows was installed at the start of this phase, use it:
install the latest 24.x and select it, then make that selection the machine default so it survives a
new shell (the plan `01-05` executor runs in a fresh session and its precondition asserts the active
runtime). If no version manager is present, upgrade the system Node install directly — `winget
upgrade OpenJS.NodeJS.LTS` is the least-friction route on this machine; the installer from
nodejs.org is the fallback if winget is unavailable or elevation is refused.

If the upgrade needs elevation you cannot obtain, stop and report the exact command the developer
must run. Do not work around the gap by disabling the CLI's version assertion, adding an npm
engine-enforcement override to `.npmrc`, or setting a version-check bypass environment variable —
any of those would leave Angular 22 running on an unsupported runtime, which is precisely the class
of problem this hardening milestone exists to remove.

After switching runtimes, reinstall `node_modules` from the lockfile with `npm ci` in

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry -> local `node_modules` | Untrusted third-party code enters the build at `ng update` and `npm ci` |
| OS package source (winget / nodejs.org installer) -> local Node runtime | A new runtime binary is installed on the developer machine |
| Build tooling -> shipped browser bundle | Whatever the toolchain emits is what executes in the user's browser |

No new *runtime* trust boundary reaches production. Per RESEARCH.md's Security Domain assessment,
ASVS V2/V3/V4/V5/V6 all evaluate to **does not apply** for this phase — a dependency-version bump
isolated from auth, session, access-control, input-handling and cryptography code (Phase 3 scope).
