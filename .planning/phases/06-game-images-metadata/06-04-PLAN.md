<objective>
Stop new imports from picking wrong IGDB matches like Portal's (IMG-03 prevention). When GameSyncManager enriches a row that has no IGDBId, it first resolves the row's SteamAppId through IGDB's external_games mapping, which is exact (D-09 step 1). Only then does it fall back to the existing exact-name-then-first-hit search, now with 10 results (D-20).

Purpose: the research scan (RESEARCH Appendix A, 2026-10-27) found 49 owner Steam rows whose stored IGDBId disagrees with IGDB's Steam mapping, a result of matching by name alone. Plan 06-02 re-runs that scan after this plan lands. An exact Steam mapping avoids that for every future match without touching rows that are already matched (D-10).

It also pages the screenshot and artwork fetch (D-21, Task 3), so image-rich batches are not cut off at 500 rows. That task moved here from 06-01 when 06-01 was split, because 06-04 already owns the other IgdbService query changes.

Output:
- `IgdbExternalGame`, `IgdbService.ExternalGamesUrl` and `FetchExternalGamesBySteamAppIdAsync` (returns the raw rows)
- the lowest-mapped-game selection and the matcher branch in `EnrichGameAsync`, with the query sorted `sort game asc`
- an Id cursor for the `GameSyncManager.RunAsync` batch loop in place of `Skip(offset)`
- `SearchGameAsync` raised from `limit 3` to `limit 10`
- `IgdbService.ImagePageSize`, the offset parameter on both image fetches, and `GameImageManager.FetchAllImagePagesAsync`
- contract tests
- `GameSyncManagerMatcherTests` (T3a-T3h) and the `ImageRichBatch_PagesScreenshotsUntilAShortPage` manager fact

Per D-09 the new IGDB query lives in IgdbService and the selection logic lives in the manager. RESEARCH ("Recommended IgdbService addition", Pattern 2) sketched a `FindGameIdBySteamAppIdAsync` returning `long?`, which would pick the id inside the service. This plan follows the locked decision instead: the service returns `List<IgdbExternalGame>` and `EnrichGameAsync` picks the id.

Not in this plan: `GameEnrichmentManager`, `SearchCoverByNameAsync` and the Add-game search UI are not touched (D-08). D-20 changes the shared `SearchGameAsync`, so `GameEnrichmentManager`'s own name search also sees 10 results. Its code is unchanged.

If wave-2 plans execute in the same checkout rather than in separate worktrees, the executor runs their `git add`/`git commit` steps one at a time, never concurrently.
