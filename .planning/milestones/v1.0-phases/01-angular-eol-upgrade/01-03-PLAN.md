<objective>
Advance `game-planner-ui` from Angular 17 to Angular 20 through three sequential single-major hops
(17 -> 18, 18 -> 19, 19 -> 20), each fully verified and separately committed.

Purpose: This band crosses the two changes most likely to be misread as forcing an out-of-scope
migration — the v19 `PendingTasks` rename (a mandatory codemod that needs no manual action) and the
v20 shift where Karma stopped being the CLI's new-project default (widely and wrongly reported as
Karma removal). Both are handled by letting `ng update` do its job and asserting the result.
Output: The app running on Angular 20, with three more bisectable hop commits.

**Target for the phase is Angular 22** — see `01-01-PLAN.md` &gt; `<target_version_resolution>`.
</objective>

<hop_protocol>
## The hop loop — identical for all three tasks in this plan

Restated from `01-02-PLAN.md` so this plan is self-contained.

1. **Update.** From `game-planner-ui/`, run `ng update` for `@angular/core` and `@angular/cli` both
   pinned to the same target major, via `npx ng` so the project-local CLI runs. Never pin TypeScript,
   zone.js or RxJS by hand — `ng update` picks patch versions inside the peer ranges, and each task's
   acceptance criteria assert the result landed in range.

2. **Decline every optional migration (D-03, D-06):** conversion of components to the standalone
   (NgModule-free) authoring format; conversion of templates to the built-in control-flow block
   syntax; the `use-application-builder` esbuild/Vite build-target switch; the Vitest test-runner
   switch; any prompt offering to drop zone.js in favour of Angular's zoneless change-detection
   provider. Accept only migrations `ng update` applies automatically as mandatory codemods. Running
   non-interactively already produces this behaviour and needs no extra flag.

3. **Peer-resolution fallback only if needed.** If `ng update` aborts with an `ERESOLVE` /
   peer-dependency conflict *before* running any schematic, retry once with `--force`. Never
   pre-emptively; never to silence a compile error. Record per-hop usage in the SUMMARY.

4. **Node runtime band.** Use the Node.js column of RESEARCH.md's hop matrix plus the strategy
   recorded in `01-01-SUMMARY.md`. Note that from the v20 hop onward the matrix admits `^24.0.0`, so
   the machine's installed Node 24 line becomes in-range for the first time in this chain. Per D-02,
   changing the local Node runtime is in scope — do not stop to ask.

5. **Verify in this order (D-04).** `npm run build`; then
   `npm test -- --watch=false --browsers=ChromeHeadless`; then the builder assertion; then a boot
   smoke check (start the dev server on port 4200, poll until it answers, confirm the served HTML
   contains the app-root element, stop the server). **A test run reporting "Executed 0 of 0" with
   exit 0 is a PASS** — this repo has zero `.spec.ts` files by design, so the check proves the
   Karma/Jasmine harness boots and the builder resolves. Only a non-zero exit or a
   harness/compilation error is a failure.

6. **Structural-preservation check before committing (D-03, D-06).** `src/main.ts` still bootstraps
   the root NgModule via `platformBrowserDynamic()`; `src/app/app.module.ts` still carries a
   `declarations:` array; `src/polyfills.ts` still imports zone.js; `tsconfig.json` still has
   `"strict": true` plus all four `angularCompilerOptions` strictness flags `true`. A mandatory
   migration proposing to loosen a strictness flag is a stop-and-report event, not something to
   accept silently.

7. **Commit exactly one commit per hop (D-05)**, message `chore(deps): upgrade Angular N-1 -> N`,
   staging only paths under `game-planner-ui/`.

Work exclusively inside `game-planner-ui/`. `GamePlanner.API/` and `Database/` stay untouched.
</hop_protocol>
